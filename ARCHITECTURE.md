# Custom Pi UI architecture

Ownership map for `extensions/`, `extensions/lib/` and `lib/ui/`, grouped by branch. Each bullet records who owns a module and the boundaries; it does not describe behavior — keybindings, labels, visuals and lifecycles live in the code, its tests, and `extensions/DESIGN.md`. Layout and verification procedures live in `extensions/AGENTS.md`.

## Rules

- **One owner per surface.** Exactly one module adapts each Pi component or screen region; two extensions never patch the same surface.
- **Shared libraries stay shared.** `extensions/lib/` and `lib/ui/` have no `index.ts` and never import extension-specific modules; only pure functions cross that boundary (jiti gives every extension its own module registry).
- **Pi owns** Unicode/grapheme measurement, escape parsing, tool execution, results, session storage and process lifetime. Wrap and adapt; never reimplement tokenizers, width tables or diff/LCS matching.
- **Retired code is deleted**, with one line under "Retired" here naming its replacement; no disabled copies are kept.

## Repository and client overlays

- This directory is the public `NextNodeSolutions/pi-agent` checkout on every machine and VM that runs Pi. `.gitignore` is an allowlist: a new top-level entry stays untracked until it is listed there, so runtime state, sign-ins and caches never reach the repo.
- `settings.pinned.json` owns the settings keys every machine shares; `bin/setup` merges them into `settings.json`, which Pi rewrites (default model, changelog version) and stays untracked. Edit a shared key in `settings.pinned.json`, then run `bin/setup`.
- `client/<name>/` holds one client's private overlay, untracked and never published: `skills/` (found through `settings.pinned.json` `skills`), `skills.json` (merged by `prompt/skill-surface/overlay.ts`) and `magpie-routing.json` (merged by `model/route/spec.ts`). `extensions/lib/client-overlays.ts` lists the overlay files; an overlay adds entries and never redefines one. Client material goes there, never into a tracked file.

## Model surface and routing

- Magpie is the router for every model request pi or its subagents make. `models.json` alone defines what models exist: the `magpie` provider exposes `group/router` (the default: Magpie's classifier labels each turn's intent and picks a tier), one group per fixed intelligence tier from fastest to strongest — `group/instant`, `group/fast`, `group/think`, `group/deep`, `group/expert`, `group/ultra`, `group/max` — to call a tier directly, and `group/mini` (trivial calls: checkpoints and session titles, both read from `context-budget.json` `summaryModel`) — the gateway picking the underlying model per group and per turn. Which models a tier group holds lives only in Magpie: read it with `magpie group <id>`, never restate it here or in a `models.json` label. The router's members, intents, ordered rules and pin phrases live only in `magpie-routing.json` and the client overlays merged into it, owned by `extensions/model/route/`. `settings.json` only references the groups — `defaultModel`, `enabledModels`, every `subagents.agentOverrides.model`, and `subagents.modelScope.allow: ["inherit", "magpie/*"]`, so a subagent cannot pin a concrete model. Thinking level has one home per fact: the session default per model in `settings.json` `modelThinkingLevels`, an agent's default in its definition frontmatter, an `agentOverrides.thinking` only where it differs from that frontmatter. Two exceptions name concrete models deliberately: the fallback chain in `extensions/model/fallback/config.json` (it must not route through Magpie when Magpie itself is down) and `PI_DEFAULT_ADVISOR_MODEL` in `skills/advisored/scripts/lib-backend-pi.ts` (the advisor must be a non-Anthropic family, which no Magpie group guarantees). Claude runs on the subscription through Magpie's `claude` provider, which starts the real `claude` binary as `claude -p` for every request (Magpie setting `claudePrintMode on`, stored in `~/.config/magpie/settings.json`): pi's instructions travel in the first user message and pi's tools are offered to it as MCP tools. Never turn Magpie's Claude Code interactive mode back on for pi: Anthropic judges pi's turns in that mode as a third-party app, bills them to extra usage and answers 400 ("You're out of extra usage") whatever the plan's headroom; Magpie returns that 400 as it came and tries nothing behind Claude in the group. Print mode costs about twice the interactive allowance per token on the plan; that is the price of pi's own prompt. No pi-side launcher or tool to Claude Code exists. Magpie's `claude` provider holds two Claude accounts: Claude Code's own saved sign-in, and a `Claude setup-token <hash>` account holding the vault's `CLAUDE_CODE_OAUTH_TOKEN` (location named by `~/.config/agent-secrets/core-vault.json` `clients.claude.path`). Magpie passes over an account that needs a new sign-in, so when the saved sign-in lapses every Claude request goes to the vault account and no `/login` is needed. `bin/magpie-claude-token-sync` owns that account: it registers the vault token, proves it answers, and removes the setup-token accounts it supersedes. The vault is the token's only definition. Rotation follows `skills/infisical/SKILL.md` section core-vault.
- `extensions/model/fallback/` owns the unified model surface (`/models`, pricing rows, the picker and its settings path) plus failover/retry. Automatic switching applies only to interactive sessions; headless children keep their own model and fallback contracts. `gateway-watch.ts` covers the failure no error reports: a Magpie gateway that accepts a request and stops answering. While an agent-turn request is silent it probes the gateway's `/models`, and only consecutive unanswered probes (thresholds in `gateway-liveness.ts`) abort the request and move the session down the chain; a slow reply from a gateway that still answers probes is never aborted.
- `extensions/model/route/` owns which group the router targets. Edit `magpie-routing.json`, then run `/route apply` on the machine that hosts Magpie: it replaces every rule of `group/router`, so a rule added with `magpie group rule` is erased by the next apply. A human prompt holding a pin phrase pins that group for the session: every request bound for `group/router` goes to the pinned group until `/route auto`, and `/route <group>` pins by hand. Magpie classifies a turn when a request ends on a user message and keeps that turn's model while the request's earlier messages stay unchanged. A `context` hook that adds text anchors it to a persisted entry and freezes it there, as `commands/goal/context-checklists.ts` does: a message ending the request makes Magpie re-classify every round, and one inserted or reworded mid-turn drops the tool rounds to the router's first member and rewrites the prompt cache.
- `extensions/model/gateway-priority/` owns the session-start warning that the Magpie gateway can be starved of CPU; it only schedules `bin/magpie-gateway-priority check`, which holds the rule: the gateway's launchd job must be `ProcessType` `Interactive`. `magpie daemon install` writes `Background`, which confines the gateway and the `claude -p` processes it starts to the efficiency cores at priority 4, so one CPU-heavy command on the host stops every session until it ends. After any `magpie daemon install`, run `bin/magpie-gateway-priority fix`.
- `model-picker-settings.ts` owns the settings write path: whole-file read-modify-write of exactly two things — one agent's override in `subagents.agentOverrides` and the saved `enabledModels` list (membership and order) — unrelated keys preserved, refusal when another writer changed the file underneath.
- Scope semantics: pi re-resolves `enabledModels` on every session start and no extension API can move the running session's scope, so edits announce the next session while the picker previews them immediately. `command-filter.ts` keeps pi's own `/model`, `/thinking`, `/scoped-models` and bundled `llama` out of the slash menu. Per-tab keys, row labels and group semantics: `model-picker-keymap.ts` and `extensions/DESIGN.md` §6.
- `agent-roster.ts` owns the agents-tab roster: it consumes `pi-subagents:agent-roster:v1` from the subagents package over pi's event bus, validates the answer field by field, and falls back to the pins it can read itself when the package does not answer.
- Inco serves GLM with thinking always on and ignores pi's level unless the request carries `reasoning_effort`: the Inco entries in `models.json` keep `compat.supportsReasoningEffort: true` and map `off` to `low`, the lowest effort Inco accepts. A `false` there silently runs every request at `max`. `extensions/ui/hud-footer/inco-session.ts` is the config's browser-session boundary (Inco publishes no balance API: it replays the machine's console session); `safari-cookies.ts` is the only browser-cookie reader. Sessions are read, never written; nothing here runs from a render path.

## Tools, guard and the workspace boundary

- `security/machine-identity.ts` owns local Universal Auth and the bound API domain. `bin/infisical` injects its token for CLI callers. The browser broker and provider resolver use that shim, while REST callers import the login directly. `security/machine-identity.json` owns credential variable names and process exit codes. Authentication usage belongs in `skills/infisical/SKILL.md`.

- `extensions/tools/guard/` owns the bash tool's job controls (admission limits, a foreground window the model can only lengthen, one progress read per running job, one completion notification delivered before the next model turn) on top of Pi's process-group cancellation and output accumulation. It governs model-issued commands only — not `!` shell input, `pi.exec` or MCP calls — and temporary receipts are evidence, not a job service.
- Guard modules are pure; the index wires them and notifies the human. `shell-guard.ts` plans the lookups typed into bash: simple shapes run through their owning tool inside `managed-bash.ts` (no round trip lost); `recovery.ts` appends the nearest match to a failed `edit` and the nearest existing directory to a failed `read`; `command-evidence.ts` saves validation logs before display filters; `read-ledger.ts` refuses a reread only while the exact successful result is still in projected context, tracking model-issued reads only — nested calls from `lookup` or `codemode` scripts (`parentToolCallId`) skip the ledger and keep the shell guard; `codemode-guidelines.ts` owns the guidelines added under the codemode tool while it is selected (output cap, failure handling, no validation inside a script, read cap, template escaping), and `script-validation.ts` refuses a validation command issued from inside a script, so the batch ends before the check runs.
- `repeat-guard.ts` is the loop breaker: it refuses a model-issued call repeated turn after turn with the same arguments, with arguments and output that differ only in their numbers, or a tool answering with the same output turn after turn, escalating from refusal to a steer message, then ending the run, then aborting it. `fixed-delay.ts` refuses a `sleep` stage between shell commands; `idle-command.ts` a command that only echoes, assigns or reads the clock. The bash description states its thresholds from the same constants.
- `extensions/tools/test-pace/` owns human request records, the `/test-pace allow` path permission and the `test_pace` tool. `extensions/lib/test-pace/` owns runner/path checks and the two Jev decisions shared with `bin/test-pace.ts`: the pace of a change (`decision.ts`) and whether the human's own request asks for tests (`permission.ts`). `tools/guard/test-writes.ts` checks every write, edit and shell command against branch-local request, grant and permission records, preserving pre-existing tests; it reads the permission once per request, on the first test write no grant covers. A request recorded in a subagent child comes from its parent agent and never carries permission. `tools/guard/shell-writes.ts` names the paths a shell command writes from its literal words (redirects, file commands, in-place editors, inline code); it recognizes test writes, not arbitrary programs. The guard is a tool policy, not an operating-system sandbox.
- `extensions/tools/lazy-load/` owns the session's active-tool set and the `load_tools` loader: UI sessions only; headless and granted subagent children keep the set their caller granted. Tool-guard respects the active set without changing it.
- `extensions/lib/runtime/` owns the workspace boundary: `anchor.ts` finds the anchor (`.workspace.json`) above a path and caches its Boat target from `workspace status --json`; `runtime.ts` routes every file and process call to the Boat for a path under an anchor (or the Boat's home) and to the Mac otherwise; `remote.ts` is the only ssh caller; `pi-operations.ts` builds Pi's tool operation sets from it. Extensions that touch the project read and run through `runtimeFor(path)`, never `node:fs` or `child_process` directly.
- `extensions/tools/workspace/` owns Pi-in-an-anchor: re-registers read/write/edit/ls/find with Boat operations and grep as Boat-side `rg` (Pi's grep spawns local ripgrep whatever its operations), routes `!` input, names the Boat checkout as cwd, wakes a stopped Boat and shows its ports as a footer status. Inert outside an anchor; `tools/guard` keeps owning bash and takes its operations from `#lib/runtime`.
- `extensions/tools/secret-output/` gates tool calls before execution using `~/.pi/agent/security/secret-policy.ts` (environment dumps, Infisical reads, credential files), shared with Claude's `PreToolUse` hook, and rewrites every tool result through `secret-redact.ts` (values of secret-named environment variables, known key formats) before the model or the session file sees it; Claude Code has no result hook, so there only the pre-call gate applies. The names-only CLI lives beside that policy and releases validated key names only: `secret-set.mjs` and `secret-move.mjs` are built on `infisical-target.ts` (ids, names, paths: one pattern each) and `infisical-rest.ts` (session token, REST calls, names-only listing). It lives in `security/` inside this repo; no extension imports from outside the repo, or Pi breaks on every machine that only has the checkout. This is an accident guard, not isolation from a process with the same OS permissions.
- `extensions/tools/tailnet-links/` owns the link conversion of the final assistant message: on `message_end` it sends the text to `tailnet-link rewrite` on the machine that holds the project (`runtimeFor(cwd)`) and replaces the message before display, and it exports `skills/tailnet-links/scripts/dev-server.env` into Pi's environment. It holds no link rule: which paths, ports and machines are linked lives only in `skills/tailnet-links/scripts/`, which Claude Code and scripts call through the same `tailnet-link` command. Those scripts also own every link the machine makes without Pi, which `skills/tailnet-links/SKILL.md` describes. A failed round trip leaves the message as written.
- `extensions/tools/worktree-cleanup/` schedules the worktree skill's cleanup after bash calls that end a PR and retries at settlement. `skills/worktree/scripts/cleanup` owns deletion checks and Git operations. `scripts/terminal close` owns terminal inspection and closure.
- `extensions/tools/lookup/` owns the `lookup` tool: several read/grep/find/ls operations in one call through `ctx.executeTool`, so every nested call keeps pi's validation and the guard hooks; it never reads files itself.

## Commands and prompts

- `extensions/commands/goal/` owns the active-branch checklist: storage/projection (`lib/goal/state.ts`), pure edits, schema, tool and command entry points, presentation. `route-events.ts` records human prompts; `context-checklists.ts` places the open-item checklist through the `context` event, never as a persisted message, frozen before each prompt and compaction summary and inside tool results at a fixed interval; `visibility.ts` owns the global display preference. Routine declaration and ticks make no remote request; the extension never schedules a turn or sends a synthetic user message. Its behavioral contract lives once, in the `goal` tool description and guidelines, not here.
- `lib/human-prompt.ts` defines which Pi input sources count as genuine human input; `extensions/commands/dump/` (above-editor receipt, retired by the next human prompt) and goal routing both consume it.
- `extensions/prompt/skill-surface/` owns the session's skill surface: the catalog filter (hidden and project-scoped skills, `skills.json` plus every `client/*/skills.json`) applied to `systemPromptOptions.skills`, and the autoload injection through the `context` event, never persisted. `lib/skills/block.ts` is the one `<skill>` block format, shared with `prompt/inline-skills/`.
- `extensions/commands/usage/` owns `/usage`: cost, calls, batching and failure counters for the current branch or the last N days of session files; read-only, rendered as an above-editor widget.
- `extensions/commands/simplify/` owns `/simplify`: deterministic file-scoped pipeline plus Jev routing for bare targets, four read-only lens children via the subagents package, findings validated, deduplicated and ranked, a human checkpoint for the rest. The extension never edits code, runs a gate or stages anything — the model does, through its own tools.
- `extensions/commands/context-budget/` owns context growth: checkpoints at completed tool batches without injecting a continuation; Pi auto-compaction disabled, native threshold/overflow attempts refused, no native-summary fallback. `decisions.ts` preserves bounded exact questionnaire receipts independently of the generated summary; `budget-writer.ts` owns the atomic settings rename; `lib/context-budget/events.ts` owns the bus channel the hud-footer gauge rereads.
- `extensions/commands/chezmoi-reconcile/` owns `/chezmoi-reconcile` and its session-start and shutdown runs; it only schedules `bin/chezmoi-reconcile`, which holds the rule (on the Mac Studio the live config is truth, so a managed target deleted live leaves the chezmoi source).

## Rendering

- `themes/catppuccin-latte.json` owns the house colors; `palette.ts` reads its `vars` — no second hex table. `theme.ts` maps colors to semantic roles; the app is fixed Latte, no runtime theme switching. `terminal-color.ts` owns parsing, blending and nested ANSI styling; the hud-footer ramps reuse it.
- `lib/ui/terminal-text.ts` owns clipping, wrapping, column slicing and hanging indent over Pi's measurement. `align.ts`, `frame.ts`, `selection-marker.ts` own shared spacing, frames and focused-row bands; frames compute their own clipping and padding — callers provide content and insets, not width metrics.
- `lib/ui/editor-decorator.ts` composes per-extension editor decorators once per `session_start` and owns the base editor factory: the first registered decorator builds it, and every caller passes it in. Decorators rebind instance methods and reassignable callbacks (pi reassigns `onChange`/`onSubmit` after the factory runs). Also owns `EMBEDDED_LOADER_FIELD_WIDTH`.
- `extensions/ui/renderers/` owns every display surface — assistant responses, all Pi tool rows, compaction cards, prompt frames and the skill callout — and never registers, replaces or executes a tool. `assistant-surface.ts` alone adapts Pi's assistant component; response classification uses provider phase metadata, never prose heuristics. Tool vocabulary: `tool-presentation.ts` (Pi tools), `package-presentations.ts` (package tools), generic fallback otherwise. Edit/write and native-image results use standalone panels on the shared content column; `tool-mouse-surface.ts` is the version-bound mouse adapter.
- Cards: `message-cards.ts` adds the transcript cards for minters that cannot import the house libraries — the vendored packages (frontend's `frontend-progress-stop`, the subagents notice family) and syneva's external `syneva-event`. The shared card panel lives in `lib/ui/message-card.ts`; `lib/ui/expandable-card.ts` owns per-card mouse expansion. An in-config producer registers its own card beside its minting extension instead, like `tools/guard/bash-job-card.ts`.
- `lib/ui/` presentation libraries (`activity-line`, `activity-timing`, `activity-details`, `change-block`, `tool-panel`, `response-divider`, `response-markdown`, `relay-line`) own the shared rendering vocabulary: the content column every surface aligns on, diff washes, typography over Pi's Markdown parser. Render functions read state; they never mutate it or do filesystem IO.
- `lib/ui/surface.ts` and `ordered-widget-stack.ts` own widget registration, subscriber notification and the single priority ladder ordering every above-editor surface. Cross-extension state lives on `globalThis` under versioned `Symbol.for` keys defined in their owning modules — bump the key when the stored contract changes, because `/reload` preserves process globals while jiti re-registers modules.
- `lib/ui/pi-runtime.ts` resolves Pi's bundled classes and owns version-drift detection (`detectPiDrift`, `AUDITED_PI_VERSION`); `pi-component-patch.ts` owns checked method replacement and restoration. Drift never blocks installation; the `pi-updated` skill re-audits the adapters and extensions against the running release.
- `lib/ui/prompt-attachment.ts` is the cross-extension attachment marker contract. `extensions/lib/attachments/` owns the scenario-neutral capture machinery (alias ingestion, thumbnails, previews, snapshot records); `prompt/attachments/` owns only the prompt wiring; the questionnaire reuses the same machinery through `questionnaire-captures.ts`.

## Human dialogs

- `lib/ui/human-dialog.ts` owns the lifetime of every dialog that blocks the agent on a human (`ctx.ui.custom` wiring, abort listener, terminal program status); `lib/ui/transcript-component.ts` is the stateless transcript renderer both tools use. `ui/ask-user-question/` and `ui/ask-user-secret/` own only their content.
- `ui/ask-user-question/questionnaire-events.ts` is the one cross-extension contract for answer/discussion mode: a raised questionnaire is the visible stop. Every questionnaire choice keeps a user-written answer path — the public schema cannot remove it.
- `ui/ask-user-secret/` is the one path for a secret typed by the human: `secret-dialog.ts` masks the entry, `secret-store.ts` parks the value in-process under a one-time, origin-bound handle, `infisical-write.ts` feeds the vault script on stdin. The issuer/claimant contract (`globalThis` key, handle pattern, TTL) lives in `~/.pi/agent/security/secret-handoff.ts`, imported by this extension and by `packages/pi-frontend-check/extensions/secret-handoff.ts`, which is the only claimant. No value ever reaches tool arguments, results, logs or the transcript.

## Vendored packages

Pi-harness tool packages are vendored under `packages/`, each the only copy — edited in place, no `.git` — with a `SOURCE.md` beside it naming the upstream revision:

- `packages/subagents/` is the vendored `pi-subagents` package (`subagent`, `bg_wait`, `subagent_supervisor`, the agent roster event, workflows). Read its `FORK.md` before changing it. It keeps its own `package.json`, `node_modules` and gates; root lint/format ignore `packages/**`; its config file stays `extensions/subagent/config.json`.
- `packages/pi-frontend-check/` owns the Brave frontend-testing tools, with the embedded `shared-web-logins/` Infisical broker executed by its `shared-vault.ts`.

Before adding or changing a vendored Pi package, read `skills/pi-updated/package-audits.md` and provide its required runtime audit entry. `pnpm run audit:pi` checks every directory under `packages/`, including packages not enabled in settings. Agent-agnostic dev tools stay out of `~/.pi/agent` (the `workspace` Boat CLI remains `~/Development/tools/workspace`, symlinked from `~/.local/bin`).

## State lifetime

Ownership facts only; behavior detail lives in the modules.

- Questionnaire dialogs own editor, navigation, responses and render cache; keyboard events mutate on the TUI event loop, render functions only read. Chat-pause snapshots are deleted on completion/cancellation and cleared on shutdown/reload; a pause emits `discussing`, reopening `answering`; the questionnaire never auto-relaunches while the user talks.
- Pi owns tool execution, results, images and global expansion state. Message-card mouse toggles stay local to their rendered instance; Pi's global toggle rebuilds them with its chosen state. `ToolRow` owns presentation state; `ToolLifecycle` freezes completion time.
- `tool-durations.ts` and `write-snapshots.ts` keep reload-stable weak caches keyed by result-content identity, with no extra session entries. `write-snapshots.ts` reads bounded before-images at `tool_call` and records comparisons at `tool_execution_end`; it never replaces arguments or results, and unknown/binary/oversized baselines fall back to labeled neutral content.
- Prompt attachment relocation happens during entry mounting, never during rendering; session entries and model image content stay unchanged, and unmatched entries remain standalone.
- Dividers and Markdown cache by width and invalidate with their owning message; streaming rebuilds presentation only, and unknown streaming responses stay neutral until completion. No animation timers.
- One session-scoped `activity-clock.ts` repainting live tool rows, deduplicated per TUI; the final completion stops its pulse, and shutdown/reload disposes it.
- `extensions/ui/herdr-status/` owns what Herdr learns about a session, as terminal labels (`hc label`), cleared on shutdown. `agent.waiting`: on `agent_settled`, from the subagents package's active-work answer and the guard's awaited shell jobs (foreground commands that outlived their window, not background starts such as servers); it never reads package state directly, only `pi.events` answers. `agent.title`: `title.ts` names the session once from its first human prompt through `pi.setSessionName` (the fast title model, else the session's), so the name lives in the pi session and every `session_info_changed` republishes it; the Herdr `agent-naming` mod (`~/.config/herdr-app/mods/`) only follows that label and never reads session files or spawns pi.
- `skills/terminal-watch/` owns watching a Herdr terminal and the lifetime of each watcher; the Workbench mod (`~/.config/herdr-app/mods/my-tabs/workbench-tab.js`) only prompts its monitor Pi to load that skill and holds no watch rule.
- The `hud-` prefix names the chat's passive status layer: `hud-status/` (working label), `hud-telemetry/` (editor-border telemetry block), `hud-footer/` (status, git and context lines). A new chat-status extension takes the same prefix; interactive input surfaces do not. `git-tracking.ts` owns live Git refresh (one abortable status read, coalesced nudges, no headless polling); `context-line.ts` renders one line, only while a `[review]` or `[PR #n]` link exists, resolving the Syneva attachment rather than assuming the cwd. On the `magpie` provider the quota strip shows the session's group and the model Magpie last served it with (`magpie-route.ts`): Magpie echoes the group in the response body, so the `x-magpie-model` response header is the only source of the served model. The timing modules own their records, aggregates and persistence; unobserved durations stay unknown.

## Boundaries

- `schema.ts` owns every tool-data shape — the LLM input schema and the canonical domain/`details` schemas; UI types derive from them via `Static`; `normalizeQuestions()` enforces semantic constraints; session replay re-validates through the same schemas, falling back to plain text when the payload is unusable.
- Public output is bounded by terminal columns, not JavaScript string length.
- Regression tests cover multiline/editor alignment, Unicode, styled wrapping, hyperlinks, narrow frames, selection markers and hud-footer color interpolation, against Pi's real editor without starting terminal IO. Verification commands: `extensions/AGENTS.md`.
